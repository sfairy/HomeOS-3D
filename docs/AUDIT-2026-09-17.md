      **范围修正**：审计原判写的是「金额改整数分」，但订单侧（`*_amount_cents`）**本来就是整数分**，
      真正浮点的是**邀请积分**子系统（钱包 / 流水 / 提现 / `orders.referral_reward_points`）。
      因此本项只动积分，订单金额一个字没改 —— 这也让「改写存量数据」的面收窄到 4 张表。

      **为什么单位取「厘」（1 积分 = 100 厘）**：厘是 1/100，正好等于积分原有的两位小数，
      所以对外 JSON 仍是 `"10.05"` 这种两位小数字符串，**逐字节不变** ——
      前端、`store.js`、`referrals.js`、后台模板都不用改（已验证：它们把该值当不透明字符串
      或 `Number()` 用）。这也是选厘而不是「分」的原因：换任何其它单位都会破坏这个性质。

      **为什么必须删掉旧列，而不能「先留着」**：旧列是 `NOT NULL` 且**没有 DDL 默认值**
      （Python 侧 `default=` 不写进 DDL）。ORM 一旦不再映射它，`INSERT` 就会省略该列，
      此后每次插入都以 `NOT NULL constraint failed` 失败 —— 且**只在存量库上**失败：
      全新库建表时本就没有这一列，本地与 CI 全绿。这正是 `schema_guard` 文档里点名的
      最难排查的漂移，所以旧列必须真正删除。`ensure_schema` 新增列时也印证了这点：
      实测里 `accounts.password_hash` 只能以**可空**列补上（它同样没有默认值）。

      **迁移为什么不是一个大事务**：SQLite 支持事务性 DDL，但 `DROP COLUMN` 内部走
      「建新表→拷数据→换名」，依赖驱动把 DDL 正确纳入事务，链路长且难验证。这里改成
      每步各自提交 + 三段顺序保证「先验证、后销毁」，任何时刻崩溃都不丢数据：

      | 阶段 | 状态 | 崩溃后 |
      | --- | --- | --- |
      | 1. `ensure_schema` 补 `*_centi`（`DEFAULT 0`） | 新旧列并存 | 旧程序照常运行 |
      | 2. 回填 + 逐行对账 | 新列已填、旧列未动 | 重跑幂等（只写不一致的行） |
      | 3. 退役旧列 | 仅在新表全表对账通过后执行 | 已删即完成 |

      对账基准刻意选**「迁移前后用户看到的数字」**：`format_centi(新值) == f"{旧值:.2f}"`，
      任何一行不符就整表跳过删列并打印前 10 处差异。

      用相关标量子查询 `(SELECT count(*) ... ) < per_account_limit` 与自增同语句执行，

      | --- | --- |
      | `limit=1`，同账号第 2 次 | 拒绝（修复前放行） |
      | `limit=2`，同账号第 3 次 | 拒绝，活跃数恒为 2 |

      | `max_redemptions` 上限 | 仍然生效 |
      | 另一账号 | 不受他人 limit 影响 |

     候选名），且刻意做成**只能向前**：`downgrade` 只删索引不还原名字，因为「哪几行原本重名」

     提示」的检查先一步拦下，真正要验证的并发处理根本走不到），又必须早于请求自己第一次写
     （SQLite 的写锁是排他的，等我们开始写之后对手就再也提交不进来了，「两个请求同时写」会
     退化成「一个先一个后」）。这样**调度顺序是模拟的，而冲突本身全是真的**：真的唯一索引、

     冲突判据两处（只看列名 / 不带表名）、迁移一处（不修复重名 → 建索引直接失败）。

     提交了 —— 挡下请求的是那道提前检查，而真正要验证的 `IntegrityError` 处理根本没执行。

     `RivalWriteSession` 的触发点与 `global_popup_state` 的隐式 flush 上。

## 六、验证方式

- Python：`compile()` 全量语法检查（121 个文件）。
- JavaScript：`node --check` 全量语法检查（162 个文件）。
- `python -m store.tools.smoke` —— 996 项断言（协议字节对齐、镜像一致性、后台 DOM 绑定、并发/阻塞/预算、枚举与配额等回归）。数量随批次增长，以实际输出为准；其中若干项由 node 驱动：JS 语法（`node --check`）、转义实现的行为实测（真跑 `htmlsafe.js` 喂恶意载荷）、后台脚本启动探针、后台渲染探针（恶意载荷下确认没有活体标签）。
- `python -m backend.tools.smoke` —— 主应用侧 199 项断言（P4 起新增）。与 store 侧是两套独立断言表，同一套做法：按需拼最小 FastAPI 应用、认证依赖与上游客户端换桩，只覆盖「能在进程内确定性验证」的东西。部分检查项自带端到端路径（例如真的调一次冻结户型快照接口；B2/B3 那组拼的是真应用并真发请求，只换掉数据库与授权服务）。**P5 第二批起多了一类观测手段**：`_RecordingDatabase` 记录每次开会话时的线程号、`_LoopTicker` 每 5 ms 自增以观测事件循环有没有被同步工作掐住 ——「有没有把阻塞活留在 `async def` 里」因此是可测量的事实，而不是靠读源码判断。**P5 第四批起又多一类**：`RivalWriteSession` 包一层真会话，在被测请求第一次写之前让「竞争对手」用另一条连接提交，用来确定性地复现「先查后写」的并发窗口（真的唯一约束、真的 `IntegrityError`，只有调度顺序是模拟的）。另有两条用 AST 做元检查：`check_every_check_is_wired`（每个 `check_*` 都被调用过）与 `check_closure_scope_writes`（闭包给外层赋值漏写 `nonlocal`，含 `async def`）。B28 那条两服务对照断言会**按路径加载商店那份实现**（生产代码仍然互不 import），把同一批请求喂给两侧逐条比对 —— 这是 4.3 C 类「刻意重复但必须同步」的唯一可执行保障。

## 附录：代码质量扫描口径

仓库内**没有**可用的 linter 作为声明依赖（`store/requirements.txt` 里 ruff / pyflakes / flake8 /
pylint / vulture / eslint 均未列入，所以 CI 里都没有），因此下面全部结论由标准库 `ast` 脚本
扫描 + 逐条 `rg` 复核得出：

1. **符号引用分析**：收集全仓库 `Name` / `Attribute` / `Import` / 字符串字面量出现次数，
   与模块级定义比对；无装饰器、无引用、无字符串引用者才计入死代码（据此排除 FastAPI 路由与 pytest fixture）。
2. **未使用导入**：按文件统计导入名与函数体内出现次数，排除 `__future__` 与 `# noqa: F401`。
3. **不可达代码**：AST 遍历各语句块，检查 `return`/`raise`/`continue`/`break` 之后是否仍有同层语句。
4. **重复检测**：采信三种口径 —— 「保留标识符后函数体逐字节一致」「同名跨文件定义」，
   以及**带三重约束的 `difflib` 相似度**（跨文件、函数名不同、双方各 ≥12 行、阈值 ≥0.85）。
   前两种抓「精确重复」，第三种抓「只差一个标识符」的近似副本；相似度口径若不加上这些约束
   会报出大量结构碰撞（曾达 140+ 组），但加上约束后全仓仅 1 对且为真（见 4.4）。
5. 每条结论均再用 `rg` 全仓库复核一次，并区分「已核实」与「需再确认」。

**P2 期间的复核手段（补充）**：开发用的 `.venv-store` 里有一个手工装的 `ruff 0.16.8`
（未进 `requirements.txt`，所以 CI 还跑不到）。用它跑
`ruff check --select F401,F811,F841 --isolated` 把上面第 2 条从「ast 统计」升级成了
**可执行的复核**，并额外抓到三类 ast 脚本看不出的东西：重复导入（F811）、
「赋值了但不生效」的闭包作用域缺陷（F841，见 4.2b），以及**引用了不存在的名字**
（F821，见 4.2 —— 这一条是 ast 脚本按设计放过的，因为静态统计只能看「有没有人用」，
看不出「这个名字在运行期能不能解析」）。
P12 接 CI 时，第一件事就是把 ruff 写进依赖并固定版本，否则同一份清单在不同环境里会漂。
第二件事是把 `--select` 收紧到能**挡住回归**的最小集合（`F`,`E9` 打底），而不是
一次性开满导致历史噪声淹没真问题 —— F821 这类「罕见分支里的名字错误」正是最值得挡的。
