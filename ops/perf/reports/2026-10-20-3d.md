# HomeOS 3D 交互渲染性能专项报告（Before / After）

- 日期：2026-10-20
- 关联：`ops/perf/reports/2026-10-20-baseline.md`、`2026-10-20-after.md`
- 环境：Apple Silicon macOS，Edge 155 headless（Playwright-Core 1.64.1），1440×900，DPR=1，`reducedMotion=reduce`；隔离实例 18801/18802
- 对象：display 页中的「3D 交互户型」iframe（scene `5ebc8e7ad16b43c8ba54caea834f82ff`，component `component-d43529e4-1e0d-4753-a5c4-6cf7b0b91bf5`）
- 边界：单 iframe、桌面 Edge、headless；**不是小米平板 8 真机**。同屏多卡（双 iframe）未测，见第 7 节。

## 1. 结论

| 维度 | 结果 | 判定 |
|---|---|---|
| 首载 stylesheet 字节 | 513,609→469,063 encoded（−44,546 B，−8.7%） | **改善**（确定性） |
| 首载请求数 | 中位 442→433（−9） | **改善**（确定性） |
| iframe ready / presented / reflections | 12,800.7→12,840.8 / 11,848→11,913 / 13,556→13,586 ms | **无改善**（在噪声内） |
| 稳态 FPS / 帧 p95 | 58.9→58.9 / 16.8→16.8 ms | **不变** |
| draw calls / triangles | 622→622 / 331,659→331,659 | **不变** |
| geometries / textures / programs | 286/30/133 → 286/30/133 | **不变** |
| webglcontextlost | 0→0（单 iframe） | **稳定** |

一句话：本轮 3D 改动（stage HTML 模板缓存、stage.js modulepreload、剥离认证四片 CSS）只拿到了**确定的 CSS 字节与请求数下降**；首帧时序、稳态帧率、draw calls 没有可验证改善。3D 的真正大头仍是「每个 iframe 先加载完整 SPA + 96 个 runtime chunk + 场景/模型/灯光缓存串行」，本轮按计划不重写 stage shell、不做共享 renderer。

## 2. 测量方法

`ops/perf/harness/bench_3d.mjs`：

1. 打开 `/display/<projectId>?performance-diagnostics=1`，等宿主 `.hb-interaction3d-runtime.is-ready`（上限 20 s）。
2. 从宿主 DOM 找到 `iframe.i3d-frame`，读取 iframe 内 `document.documentElement.dataset.performanceDiagnostics`（舞台自带的 `publishRenderStats`，每 750 ms 更新）。
3. 等 `renderer.info.render.calls > 100`，确认场景已挂载。
4. 在 iframe 内选**真正的 WebGL canvas**（宽>500、高>100 且 `getContext('webgl2'|'webgl')` 成功），派发 `pointerdown → pointermove×12 → pointerup`，触发阻尼/交互；等 2,200 ms 后每 500 ms 采样 3 次。
5. 同时采集 CDP 网络（encoded bytes / byType / 请求数）、iframe 内 long task、`webglcontextlost`、console error、JS heap。
6. 每侧 3 次独立运行，取中位数。

> 关键修正：早期脚本选第一个 width>1000 的 canvas，命中的是 2D 灯光缓存 `preview-light-cache`（1999×1350），拖拽无效，`frame.samples=0`。现在按 WebGL 上下文选 canvas，才能拿到交互稳态帧。舞台实际有 4 个 canvas：`plan-canvas`(1×1)、`preview-light-cache`(1999×1350, 2D)、`preview-render-shield`(0×0)、真正的 WebGL 画布(1999×1350, parent `#preview-3d`)。

## 3. 稳态帧指标（A/B 中位数）

| 指标 | HEAD（abf-old） | CURRENT（abf-new） | 说明 |
|---|---:|---:|---|
| frame samples | 51 | 51 | 交互后采样 |
| average FPS | 58.9 | 58.9 | 60 Hz vsync 附近 |
| median FPS | 59.9 | 59.9 | 同上 |
| frame p95 | 16.8 ms | 16.8 ms | 受 vsync 限制 |
| CPU render average | 31.98 ms | 30.66 ms | 三轮方差大（30.5–33.0），不宣称改善 |
| CPU render p95 | 38.4 ms | 30.9 ms | HEAD 21.0–39.4 / CURRENT 21.4–32.8，噪声大 |
| GPU render average | 4.91 ms | 5.16 ms | 4.75–5.30，噪声内 |
| GPU status | 可用 | 可用 | — |
| draw calls | 622 | 622 | 完全一致 |
| triangles | 331,659 | 331,659 | 完全一致 |
| lines | 0 | 0 | — |
| geometries | 286 | 286 | — |
| textures | 30 | 30 | — |
| programs | 133 | 133 | 同轮次可比；baseline 的 215 是更晚的渲染阶段快照，不与本轮直接比 |
| canvas / CSS / DPR | 1999×1350 / 1333×900 / 1.5 | 同左 | 未改渲染参数 |
| webglcontextlost | 0 | 0 | 单 iframe |

- 首帧瞬时峰值：baseline 记录 3,068 calls / 2,016,494 triangles（多 pass 叠加），稳态 622 / 331,659。本轮 A/B 的 `firstRender` 快照分别是 747 / 337,921（old）与 3,068 / 2,016,494（new），差异来自**采样时刻落在不同渲染阶段**，不是性能回归；因此只用稳态帧做前后对比。该采样点不确定本身是后续要修的观测问题（应在固定 phase 埋点）。
- 交互前后 CPU/GPU 的波动说明：headless Edge + 共享机器上，renderer 内部计时受调度影响，p95 只能看趋势，不能当硬指标。

## 4. 时序（A/B 中位数）

| 阶段 | HEAD | CURRENT | Δ |
|---|---:|---:|---:|
| iframe ready | 12,800.7 ms | 12,840.8 ms | +40.1 ms（+0.3%） |
| stage mounted | 2,083 ms | 2,136 ms | +53 ms |
| presented | 11,848 ms | 11,913 ms | +65 ms |
| reflections ready | 13,556 ms | 13,586 ms | +30 ms |
| display first-screen ready | 13,055 ms | 13,103 ms | +48 ms |

baseline（before，3 次中位）作参考：module-ready 402、renderer-created 1,026、draft-fetched 1,174、stage-mounted 1,184、settled-frame 5,836、presented 9,744、entry-finished 9,922、reflections-ready 11,062、display-first-screen 11,405 ms。A/B 轮次整体比 baseline 慢约 2–3 s，是系统负载/缓存状态差异；同轮 HEAD vs CURRENT 的对比才有效，且差异均在噪声内。

为什么 modulepreload / HTML 缓存没有可测收益：
- stage.html 本身要等宿主创建 iframe 后才请求；此前的 SPA 引导、路由懒加载、`stage-startup` 仍占关键路径。
- stage.js 的 modulepreload 只能提前网络请求，无法提前 `mountStage` 之后的场景 fetch、模型 build、灯光缓存（`light-cache-ready` 约 11.7 s）等主开销。
- HTML 模板缓存只省一次 `read_text`（毫秒级），淹没在噪声里。
- 首帧真正的大头是 `settled-frame`（约 5.8 s）到 `presented`（约 11.8 s）之间的灯光/反射/入场工作；这部分本轮没有改动。

## 5. 首载网络（A/B 中位数）

| 指标 | HEAD | CURRENT | Δ |
|---|---:|---:|---:|
| 请求数 | 442 | 433 | −9 |
| Stylesheet encoded | 513,609 B | 469,063 B | **−44,546 B（−8.7%）** |
| Script encoded | 2,016,905 B | 2,017,049 B | +144 B |
| Document encoded | 7,779 B | 7,715 B | −64 B |
| XHR encoded | 53,140 B | 53,140 B | 0 |
| Fetch encoded | 490,862 / 1,740,921（随缓存状态） | 490,794 / 1,740,853 | 不可比 |
| 总 encoded | 3,187,691（中位，但受 Fetch 缓存影响） | 4,308,203 | **不可用作结论** |
| 失败请求 | 4–9 | 4–9 | 与基线一致的静态 404，非本轮引入 |

- Stylesheet 的下降来自 stage.html 剥离认证四片 CSS（raw 125,177 B / gzip 36,899 B）；encoded 口径还叠加了 gzip、缓存与重复加载，故为 −44,546 B。
- Fetch 字节在 490 KB 与 1.74 MB 之间跳变，是场景/模型/灯光资源的缓存状态不同；跨运行总字节不可比，报告只采用确定性的 byType。
- Script 基本不变：stage runtime 仍是 96 chunk / 605,746 B raw / 234,127 B gzip（stage.js 本体 76,765 B / 21,346 B gzip，直接 import 56 个 chunk），本轮没有拆包。

## 6. 每个 iframe 的固定结构开销

| 项目 | 体积/数量 | 说明 |
|---|---:|---|
| SPA 外壳首屏 modulepreload | 8 个 / 710,839 B raw / 237,615 B gzip | 每个 iframe 都要付 |
| SPA 首屏 CSS | 336,707 B raw / 79,067 B gzip | 本轮剥离认证四片后减少约 125 KB raw |
| stage runtime | 96 chunk / 605,746 B raw / 234,127 B gzip | 静态 import 图，面板/设备模块全量拉入 |
| stage.css | 119,418 B raw / 20,979 B gzip | 舞台专用 |
| 稳态渲染 | 622 calls / 331,659 tris / 286 geoms / 30 textures / 133 programs | 单 iframe |
| WebGL 上下文 | 1 个/iframe | 同屏 N 卡 = N 个上下文 |

结论：3D 首帧不是「一个 stage.js 没预载」的问题，而是**整个 SPA + 全量 runtime 图 + 场景/灯光流水线**的叠加。要拿到数量级改善，必须动结构（独立 stage shell、共享 renderer、按设备类型懒加载面板、同屏卡上限/离屏 LRU），这些都超出本轮低风险范围。

## 7. 未测项与后续建议

1. **同屏多卡（双 iframe）未测**：需要构造两个 display 卡片或等效宿主握手；当前 display 数据只有 1 个 3D 组件。不能把单 iframe 的 FPS 当作多卡数据，也不能宣称“多卡不退化”。
2. **真机（小米平板 8）未测**：桌面 Edge headless 的 FPS/CPU 与平板 GPU 差异大；真机需采 LCP、TBT、INP、逐 iframe renderer.info、webglcontextlost。当前报告明确标注待补。
3. **独立 stage shell**：可去掉 SPA 的 8 个 preload 与认证/非舞台 CSS，但需复刻 studio-boot/renderer/apply 逻辑（studio-app 2 万行），高风险；建议 feature flag + 像素对比后再上。
4. **共享 renderer / 离屏 LRU / 同屏卡上限**：能直接降低多卡 CPU/GPU/上下文数，但改变渲染模型与像素结果，需产品确认与真机 A/B。
5. **固定 phase 的首帧采样**：`firstRender` 在 747 与 3,068 calls 之间跳变，建议在 `presented`/首个稳定帧固定打点，避免后续报告误读。
6. **面板懒加载**：`mountStage` 会无条件构造 speaker/tv/device/nas/lock/cover 面板，改动态 import 不省首屏；要省必须改成按设备类型条件构造，属行为变更，本轮不做。
