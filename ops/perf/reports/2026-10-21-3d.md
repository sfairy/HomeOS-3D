## 3. D2「渐进呈现」实验与回滚（本轮最重要的结论）

### 3.1 设计

`settled-frame` 时场景已完整画出，但原流程必须 `await waitForStageReady()`（等灯光缓存烘焙）才交 `presented`。实验把交帧提前到 `settled-frame`，烘焙完成后在后台补一帧终帧（新相位 `presented-baked`），并让 `whenPresented()` 的 promise 提前 resolve，使宿主提前收起启动层。开关：URL `stage-progressive=0/1`、localStorage `homeos.stage.progressivePresent`，默认开，可运行时关。

### 3.2 交替 A/B（3 轮，同一后端源码，只换前端产物）

| 指标 | round1 before → after | round2 | round3 | 判定 |
|---|---|---|---|---|
| `presented` | 2,086 → **1,501** | 1,923 → **1,494** | 1,996 → **1,550** | 提前 ~500 ms ✔ |
| `light-cache-ready` | 2,070 → **2,524** | 1,907 → **2,549** | 1,980 → **2,651** | **变慢 ~570 ms** ✘ |
| `reflections-ready` | 2,276 → **2,742** | 2,107 → **2,749** | 2,183 → **2,881** | **变慢 ~600 ms** ✘ |
| `display` 首屏就绪（用户真正看到） | 3,059 → 3,029 | 2,881 → **3,038** | 2,908 → **3,109** | 略差 ✘ |
| 稳态 FPS | 57.5 → **55.4** | 58.4 → **55.4** | 58.4 → **55.5** | **下降 3 fps** ✘ |
| CPU 提交均值 | 9.93 → 11.97 | 10.10 → 11.29 | 10.74 → 12.45 | 上升 ✘ |

### 3.3 归因

提前交帧会让入场动画（`startupPresentation.start()`）与后续的 `renderStudioFrame()` 在灯光缓存仍在烘焙时就开始出帧，两者与烘焙争用主线程/GPU，导致烘焙和反射装配各推迟约 0.6 s。结果是「`presented` 这个里程碑提前了，但画面真正稳定、宿主真正可交互的时刻更晚」，并且稳态 FPS 掉 3 帧。也就是说：**它优化的是日志时间戳，不是用户体感**。

### 3.4 处置

- `studio-render-loop.ts` 已恢复到原实现（`git diff` 对该文件为空）。
- 开关模块 `runtime/core/stage/progressive-present.ts` 已删除。
- 前端产物与基线**逐字节一致**（8,614 个文件 diff 为空，体积预算九项数值一致，runtime chunk 数回到 267，未引入 `presented-baked` 代码）。
- harness 保留 `presented-baked` 字段与阶段表项：它是测量能力，正式路径恒为 `null`，不影响任何门禁。

### 3.5 如果以后还要做

前提是先解决争用：把烘焙放到 Worker / 独立的离屏任务，或让入场动画在 `presented-baked` 之后才开始。只调「谁先发消息」不会有收益——这正是本轮数据证明的事。

## 4. D3 / D4（stage 依赖图瘦身 + preload）为什么不做

1. **124 个 chunk 是契约，不是浪费**：stage 运行期由 `frontend/vite.runtime.config.ts` 单独构建，`modules/runtime/` 下**每个 `.ts` 都是一个稳定 URL 的 entry**（后端 `modules/interaction3d/api.py` 与运行时按 URL 取模块）。合并 chunk 会破坏这个契约。
2. **体积已经很小**：124 chunk 合计 271,210 B encoded，全部在 `module-ready`（430 ms）之前完成。把它当作首帧瓶颈不成立。
3. **首帧瓶颈不在网络**：`settled-frame` 比 `stage-mounted` 晚 878 ms，是场景构建/几何装配；preload 更多 chunk 只会和主线程争带宽，不会减少这一段。
4. 因此 D3/D4 的预期收益接近 0，改动面却是构建契约——**判定不做**，并把上面的数据留作下次决策依据。

## 5. 未解问题（留给下一轮）

| 问题 | 现状 | 建议 |

| 3D 视觉回归 | 本 harness 的 `stage.png` 在 WebGL iframe 内恒为黑，无法用于视觉断言 | 改用 CDP `Page.captureScreenshot` 的 `fromSurface` + `--use-gl=angle`，或在舞台页内 `canvas.toDataURL()` 取帧 |
