# HomeOS 双项目性能基线报告

- 日期：2026-10-20
- 基线提交：`efc0defc`（工作树 clean；本轮只改测量工具，未改生产代码）
- 环境：Apple Silicon macOS，Edge 155 headless（Playwright-Core 1.64.1），Python 3.15（`.venv-store/bin/python`），隔离端口 18801/18802
- 隔离数据：`/tmp/homeos-perf/env/before/`，从 `homeos/data` 与 `homeos-store/data` 的 SQLite backup 复制；插入固定测试会话；`ha_connections.is_active=0` 断开外部 HA
- 原始结果：`/tmp/homeos-perf/results/before/{backend,frontend,3d,contracts}.json`
- 不可变构建快照：`/tmp/homeos-perf/before-dist`（77,084 KB homeos / 3,944 KB store）

> 重要边界：本报告所有数字是**本机隔离实例 + 桌面 Edge** 的可复现基线，不是小米平板 8 真机数据。真机 LCP/TBT/INP、逐 iframe renderer.info、webglcontextlost 仍标注为待补；禁止把本机数字写成真机结论。展示页的 `frontend.json` display 路由测到的是启动 splash（LCP=0），不能当 3D/展示页基线；3D 以 `3d.json` 为准。

## 1. 测量方法

### 1.1 后端
- 进程：`ops/perf/harness/bench_backend.py` 启动两个隔离 uvicorn（`HOMEOS_DATA_DIR`、`HOMEOS_FRONTEND_DIR`、`STORE_DATA_DIR`、`STORE_STATIC_DIR`），`LICENSE_REQUIRED=0`。
- 端点：每个端点 20 次预热 + 100 次串行 + 200 次并发（32 workers），keep-alive；记录 p50/p95/p99、RPS、错误率、响应字节。
- DB 次数：请求前后 scrape `/metrics` 的 `homeos_db_queries_total` 差值 / 请求数；store 无该指标，标 null。
- 资源：macOS `proc_pidinfo` 读 RSS/线程；CPU 用 taskinfo 的 user+system 时间差 / 测量窗口。
- 启动：wall time 为 spawn 到 `/health/ready` 可用；应用内 `homeos_startup_duration_ms` 为 lifespan 自报。`boot_import_ms` 当前未埋点（null）。
- 契约：`ops/perf/harness/check_contracts.py` 断言状态码、响应键、iframe 鉴权；ETag 检查在基线时 SKIP（尚未实现）。

### 1.2 前端
- `ops/perf/harness/bench_frontend.mjs`：Edge headless，1440×900，DPR=1，`reducedMotion=reduce`；每个路由独立浏览器，cold（新 context）与 warm（同 context 再导航）。
- 采集：PerformanceObserver 的 LCP/CLS/longtask/Event Timing，Navigation Timing，CDP `Network.responseReceived` encoded bytes，`Performance.getMetrics` JS heap，DOM 节点/iframe/canvas 数。
- 3D：`ops/perf/harness/bench_3d.mjs` 打开 `/display/<projectId>?performance-diagnostics=1`，等待宿主 `.hb-interaction3d-runtime.is-ready`，读取 iframe 内 `documentElement.dataset.performanceDiagnostics`；在舞台 frame 内对 width>1000 的渲染 canvas 派发 pointerdown/pointermove×12/pointerup，再采样 3 次。3 次独立运行取中位数（`aggregate_3d.mjs`）。

### 1.3 构建体积
- `bun run check:bundle-budget`（`ops/checks/check_bundle_budget.mjs` + `bundle-budget.json`），对 `dist` 统计 index、首屏 modulepreload、入口 chunk、首屏 CSS、runtime chunk 数/字节。
- `du -sk` 统计 dist 总体积；`find` 统计文件数。

## 2. 后端基线

### 2.1 启动与资源

| 指标 | homeos | homeos-store | 说明 |
|---|---:|---:|---|
| wall 启动（含 import） | 638.49 ms | 496.64 ms | spawn → /health/ready |
| 应用内 lifespan 自报 | 102.27 ms | 未采集 | 仅 homeos 有 gauge |
| boot import | 未埋点 | 未埋点 | 需 P0 埋点 |
| 测量窗口 CPU | 98.66%（单核饱和） | 37.36% | 32 并发压测窗口 |
| 测量窗口 RSS 增量 | +480 KB | +64 KB | 无泄漏迹象，但只覆盖 55 s |

结论：`homeos_startup_duration_ms=102 ms` 只是 lifespan 的一部分，wall 638 ms 里约 536 ms 在 import/构造/首个请求之前；当前观测面无法回答“30% 启动下降”来自哪一段，必须先补 `boot_import_ms` 与逐 phase 计时。

`/store/v1/products` 与 `/features` 同为公开轻量端点，但 products 并发 p50 是 features 的 8.2 倍、RPS 只有 12.6%。差异不是网络，而是 products 每次 4 次 SQLite 查询 + 无缓存；这是 store 后端最明确的资源效率瓶颈。

## 3. 前端基线

### 3.1 首屏（Edge，cold / warm）

| 路由 | cold FCP | cold LCP | cold longtask 总时长/最大 | cold 请求数 | cold encoded bytes | warm LCP |
|---|---:|---:|---:|---:|---:|---:|
| `/`（home） | 2,896 ms | 3,820 ms | 1,952 / 1,153 ms | 463 | 3,342,352 | 712 ms |
| `/display/{id}`（splash，不可用） | 1,504 ms | 0 | 4,956 / 3,092 ms | 445 | 3,107,747 | 0 |
| `/login` | 580 ms | 4,448 ms | 0 | 89 | 1,212,300 | 428 ms |
| store `/` | 2,528 ms | 2,528 ms | 0 | 43 | 1,096,901 | 216 ms |

关键观察：
- home cold 有 463 个请求、3.34 MB encoded、1.15 s 单次长任务；这不是“JS 入口太大”单一问题，而是首屏即拉起 3D/流媒体/图表等大量资源。
- `/login` LCP 4,448 ms，FCP 只有 580 ms，说明首屏后半段有一个大图/字体/背景在 LCP；且登录页 cold 请求 89 个，仍有优化空间。
- store home LCP 2,528 ms 与 FCP 相同，Font 716,340 B 是最大传输项；当前已用 media=print + onload 延迟非关键 CSS，但字体仍是 LCP 关键路径。
- display 的 `frontend.json` 数字来自启动 splash，不能用于 3D 结论；真实展示页就绪时间见 4.2。

## 5. 瓶颈排序（收益/风险）

| 排名 | 瓶颈 | 证据 | 预期收益 | 风险 |
|---|---|---|---|---|
| P0 | 无 HTTP 路由直方图、无启动分阶段埋点 | /metrics 只有总量；wall 638 ms vs 自报 102 ms | 让后续优化可归因，避免把噪声当收益 | 低 |
| P1 | 鉴权 2 次查询 + 授权 2 次查询叠加在每个受保护请求 | assets 0 业务 DB 仍 4 查询；draft 6 查询 | 受保护端点 DB 查询 −25%~−50%，并发 p95 下降 | 低~中（吊销延迟） |
| P1 | store products 每次 4 查询、无缓存/ETag | 并发 p50 69.5 ms vs features 8.5 ms；RPS 450 vs 3,573 | p50 −80%+，RPS 3~6×；商品写后立即可见（短 TTL + 写失效） | 低~中 |
| P2 | 展示页草稿/素材每次都 cache-buster + no-store | `?_=Date.now()` + `cache:no-store`，37.5 KB 草稿每次重下 | 二次进入省 37 KB + 1 个 RTT；304 空 body | 低 |
| P2 | 非认证首屏付认证 JS/CSS | views-auth 119,846 B；认证 CSS 125,177 B | 非认证首屏 −约 245 KB raw / −74.7 KB gzip | 低（需截图对比） |
| P2 | 启动 15 阶段串行 | lifespan 1166-1186；security/channels/weather 内部串行 | 启动 wall 目标 −30%，需分阶段证明 | 中（依赖顺序） |
| P3 | 3D iframe 完整 SPA + 96 chunk | 446 请求 / 4.34 MB encoded；首个 3D 11.4 s 才 first-screen | 早期 preload stage.js、瘦身认证资源；不改渲染结构 | 中 |
| P3 | 同屏多 3D iframe 独立 WebGL | 每卡独立 context，display 可多卡 | 本轮只测量与报告，不改共享 renderer | 高 |

## 6. 基线的已知缺口

1. 真机（小米平板 8）LCP/TBT/INP、逐 iframe renderer.info、webglcontextlost 未采集；需真机 USB/远程调试补测。
2. 展示页 `frontend.json` 的 display 行是 splash 指标；真实展示页以 3D `displayFirstScreenMs` 和 after 的专用 display 采集为准。
3. store 没有 `db_queries_total` 指标，DB 次数由代码静态计数（products 4 次）；after 可加 store 侧直方图/计数，但本轮不强行改 store 观测面。
4. `boot_import_ms` 为 null；P0 埋点后才有 import 段数据。
5. 3D 基线是 Edge headless + ANGLE Metal；真机 GPU 不同，FPS/draw calls 不能直接外推。
6. 契约基线 32 项通过、5 项 ETag SKIP 是预期的“优化前”状态；after 必须把 5 项变为 PASS。
