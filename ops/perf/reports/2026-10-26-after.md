## 3.6 三轮：展示端按草稿裁剪组件族（2026-10-26 收尾）

**拆了 chunk 却照样全下**，展示端（只挂一块 3D 户型 + 日志墙）白付 8 个族的字节与解析。
本轮改成「谁需要谁加载」：

- `componentFamiliesForDocument(doc)`（`registry/component-families.ts`，零 import 的纯函数）
  递归收集 `sharedComponents` / `pages[].components` / `children` 里的组件类型，折成族名；

- `PanelRenderer.setDocument` 末尾兜底：本次真的补到新族才补一次重渲染（已就绪不重排）。

## 5. 结论与需要记住的三件事

1. **P1-P5 的验收指标写错了口径。** 计划要求「`presented` draw call 3,068 → 接近稳态 622」，
   但 622 是**稳态帧**；`presented` 首帧包含阴影图与首次反射捕获，每帧预算只削减「所有记录同时
   变脏」时的重复捕获，不会降低首帧。本轮实测 3,084（与基线持平），稳态 625。
   真正可用的验收是「相机/灯光变化后的稳态帧 draw calls」，harness 的 `afterInteraction` 段已覆盖。
2. **`settled → light-cache` 从 +445 变成 +622 ms，需要盯。** 可能是每帧预算把重捕获插进了
   烘焙窗口，也可能是 ±7% 漂移；下次改动这块时要先跑两轮同目录取方差，再判断方向。
### 5.1 反射「推迟捕获」A/B：判定为**无效且有害**，已回退

计划里给 P1-P5 留的开关（`?defer-reflections=1` → `createGroundReflections({ deferStartupCaptures })`）
在 `audit2` 环境上各跑两轮对比（同一构建、同一草稿，仅 URL 不同）：

| 运行 | presented draw calls | 稳态 draw calls | `presented` | `light-cache-ready` | 首屏 | FPS | 稳态反射捕获 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 默认（关） ×2 | 3,084 / 3,084 | 625 / 625 | 1,937 / 1,978 ms | 1,921 / 1,962 ms | 2,627 / 2,658 ms | 58.4 | **162 次 / 545.6 ms** |
| 开启（defer） ×2 | 3,084 / 3,084 | 625 / 623 | 2,050 / 1,979 ms | 2,032 / 1,962 ms | 2,717 / 2,571 ms | 59.2 | **0 次 / 0 ms** |

结论两条，都是硬数据：

1. **首帧一分没省**：`presented` 的 draw calls 两边同为 3,084，阶段耗时差异在 ±7% 漂移带内。
   原因是首帧的反射捕获本来就不在 `presented` 之前发生（`presented` 早于 `onAfterRender`
   的首次捕获），闸门拦不到任何工作。
2. **开关打开后反射永远不建**：稳态 `captures` 从 162 掉到 0。解除闸门挂在
   `onAfterRender` 的 `ctx.reflectionDetailMode === 1` 分支上，而展示端（iframe 内嵌）
   是 `reflectionDetailMode = 0` —— 条件永不成立，闸门永不解除，地面反射永久缺失。
   这是个「只有 A/B 才能发现」的静默画面回退，`check:perf-budget` 的
   `steadyReflectionCaptures ≥ 1` 就是为它加的（开启后会直接红成 0）。

因此**回退该开关**（`studio-ground-reflections.ts` / `studio-render-loop.ts` 恢复原状），
而不是留着一个默认关、打开就掉画面的死代码。`bench_3d.mjs` 保留 `--query` 透传能力，
以后做同类 A/B 不必再改代码。

3. **本轮新增了性能预算门禁**：`bun run check:perf-budget`（`ops/checks/perf-budget.json`，
   默认取最近一次带 `3d.json` 的结果目录），阈值按漂移带留白，拦「数量级回退」。
