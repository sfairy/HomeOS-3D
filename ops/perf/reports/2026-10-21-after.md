# HomeOS 双项目性能优化（Round 2 / After）

- 日期：2026-10-21
- 基线：`ops/perf/reports/2026-10-21-baseline.md`（同一台机器、同一隔离环境、同一天）
- before 源码：`/tmp/perf-r2-before`（`git archive 9ab13c9e`），before 产物：`/tmp/perf-r2-dist-before`
- after：当前工作树 + 本轮全部改动
- 测量方式：**交替配对 A/B**（before/after 交替重启，服务器与客户端同机），因为本机存在 ±10–60% 的时辰漂移；单轮绝对值不可比，只认配对中位数与代码级可证量（DB/req、字节数、chunk 数）。

## 0. 一句话结论

后端把每个受保护请求的**固定许可读库**从请求路径移走（DB/req 全面 −1），并把 Pillow 与 websockets 从冷启动导入链里摘掉，得到 **受保护接口 p50 −17%…−36%、吞吐 +23%…+109%、import −9.5%**；未改动的对照接口全部落在 ±9% 噪声带内。前端与 3D 产物**逐字节未变**（8,614 个文件 `diff -rq` 为空），3D 里的「渐进呈现」经 A/B 判定为负收益并已完整回滚。

### 1.3 改了什么

**B1 · Pillow 延迟导入**

`api/assets.py` 的模块级 `from PIL import Image` 是整条 import 链里最贵的一项（`-X importtime` 归因：`src.api.assets` 累计 28.2 ms，其中约 23 ms 是 PIL）。
- `api/assets.py`：模块级导入 → `_load_pillow()` 门面，在 `effect_variant_payload`、`validate_uploaded_image` 两处使用点调用；HEIF 注册一并搬进去。
- `modules/interaction3d/render_cache.py`：`write_cache` 内局部导入。
- 影响面：只有真正上传/裁剪/写渲染缓存的请求才付这 23 ms；首屏、健康检查、项目草稿完全不再碰 PIL。
- 回滚：把两处 `from PIL import ...` 挪回模块顶部、删掉 `_load_pillow`。

**B2 · websockets 延迟导入**

数据来自 importtime：`websockets` 链累计 19.6 ms，而只有 HA WebSocket / 摄像流中转 / 连通性探测用得到。
- `domains/ha/integration/client.py`：模块级 `import websockets` → `_websockets()` 惰性门面（异常元组里的调用只在异常真正抛出时求值）。
- `domains/ha/integration/service_support.py`：两个失败分类函数内局部导入。
- `domains/ha/integration/connection_setup.py`：`has_ha_greeting` 内局部导入。
- `domains/proxy/ws_proxy.py`：`Subprotocol` 只出现在 `cast()` 的字符串标注里 → `TYPE_CHECKING`。
- `api/go2rtc.py`：`connect` / `InvalidStatus` / `Origin` 三处使用点局部导入。
- 影响面：REST-only 部署不再加载 websockets 客户端；首次真正建 WS 时多一次 `sys.modules` 命中（微秒级）。
- 回滚：恢复各处模块级 import。

**B3 · 许可状态读取移出请求路径（本轮最大收益）**

`LicenseService.allows()` 原先每次调用都先 `session_factory()` + `SELECT * FROM LicenseState LIMIT 1` 才查允许缓存——缓存键需要 `(lease_id, lease_sequence)`，而这两个值只存在于库里。于是每个受保护请求都固定多出 1 次 SQLite 读 + 1 次连池取用。
- `domains/license/service.py`：新增 `_identity_snapshot`（`(expires_at, lease_id, lease_sequence)`，TTL 与 `_allow_cache` 相同的 2 s），`allows()` 命中即返回，不再开 session；`invalidate_allow_cache()` 同时清空该快照。
- 语义边界：陈旧窗口 ≤2 s，**与原 `_allow_cache` 完全一致**，没有额外放宽。四条终态路径（激活、REVOKED、INSTANCE_CHANGED、ACCESS_EXPIRED）本来就会调 `invalidate_allow_cache()`，因此吊销仍然即时生效。
- `allows(database=...)`（调用方自带 session 的分支）保持原样，不改。
- 影响面：`DB/req` 在 7 个受保护端点上各减 1（见上表），是台账级的可证量。
- 回滚：删除快路径分支与 `_identity_snapshot`，`invalidate_allow_cache` 恢复为只清 `_allow_cache`。

**B4 · SQLite 读侧 PRAGMA**

`platform/core/database.py#_configure_sqlite` 追加 `cache_size=-16384`（16 MB 页缓存，默认只有约 2 MB）、`mmap_size=134217728`（只读映射，失败自动退回普通 I/O）、`temp_store=MEMORY`。
- 影响面：读多写少的墙屏负载；每条连接上限 16 MB 页缓存（按需增长，非预分配）。
- 回滚：删掉这三行 PRAGMA。
- 说明：B4 与 B1–B3 在同一轮一起上线，**没有单独归因**。它不改变查询条数，因此上表的 `DB/req` 变化全部来自 B3；p50 的改善里 B4 的份额无法从本轮数据中分离，故不作单独收益宣称。

**B5 · 剩余阻塞调用外移：结论是不需要改**

对 `api/` 下所有 `async def` 做了 AST 扫描（`sleep` / `run` / 文件读写 / `stat` / `unlink` 等）。命中的全部是：`await asyncio.sleep(...)`（5 处，本来就不阻塞）、已 `run_in_threadpool` 包裹的调用、以及错误清理分支里的 `chmod/exists/unlink`。仓库已有 50 处 `run_in_threadpool` / `asyncio.to_thread`。**没有发现需要新外移的热路径阻塞调用，因此本项不做改动**（避免为「有工作量」而引入风险）。

## 2. 前端

### 2.1 结论：产物逐字节未变


### 2.2 指标（同一 harness、同一环境）

| 路由 | FCP before→after | LCP before→after | CLS | INP p75 | 请求数 | encoded 字节 |
|---|---|---|---|---:|---:|---:|---:|
| home | 380 → 384 | 592 → 616 | 0.1816 → 0.1764 | 16 → 0 | 483 → 476 | 4,363,934 → 4,089,390 |
| display | 312 → 356 | n/a（0） | 0 → 0 | 0 → 0 | 447 → 448 | 4,162,476 → 4,164,649 |

### 2.3 计划里 F1–F3 的实际处置（有证据的不做）

- **F1「解除挂载阻塞」**：主应用仍在 `loadFrontendConfig().then(mount)`，入户认证页早已是「先挂载再拉配置」。基线显示 login（不等配置）FCP 288 ms、store-home 132 ms，而 home 380 ms——差值不足以把「等配置」定为首屏主因（`/api/v1/public/config` 服务端 p50 不到 1 ms）。**在墙屏上提前挂载会让 stores 用默认参数初始化再回填，属于可见抖动风险**，故保留现状，只把它记为「配置慢时的空白窗口」问题（启动层已由 `boot-guard.js` 覆盖）。
- **F2「首屏 CSS 拆分」**：核查后首屏 CSS 336,707 B 中 164,295 B 来自 `main.ts` 的全局样式；最大的两块可拆候选是 `list-page.css`(19,500) + `list-page-views.css`(19,349)。但 `list-page__*` 被 `NotificationCenter.vue`（墙屏通知中心组件）和 `OverviewSidebar.vue` 使用，拆到懒加载会在这些组件首次出现时闪样式；而 `list-page-views.css` 与 8 个列表页的既有主题表存在层叠顺序耦合。**收益约 7 KB gzip，风险覆盖 8 个页面 + 墙屏组件，判定不做**。
- **F3「index.html 阻塞资源」**：已由 Round 1 实现且验证有效——`bootstrap/spa_static.py` 按路由剥离认证场景四片（约 125 KB / 37 KB gzip，全部 render-blocking）。实测 home/display 各 6 个阻塞资源、login 10 个，与剥离逻辑一致。剩下的 `boot-guard.js`(22.5 KB) 必须在入口 module 之前执行才能捕获加载失败并显示兜底面板，`scene-depth.js`(657 B) 必须在首帧前挂 `.hos-touch`；两者都不是可优化项。
- **F4「按 INP 修交互热点」**：实测 INP p75 = 16 ms、交互到首帧 0.2–9.2 ms、长任务 >50 ms 极少。**没有可修的热点**，不做。
- **F5「收紧体积预算」**：本轮产物一字未动，收紧预算没有依据（会把噪声写成门槛）。保持原值。

### 已知限制（不要当成通过）

1. **不是真机**：桌面 Edge、DPR=1、1440×900。真机（小米平板 8）的 LCP/TBT/INP 与逐 iframe GPU 仍未测。
2. **3D 截图不可用**：`stage.png` 在 before/after 两张里都是全黑（Playwright 对 iframe 内 WebGL canvas 的合成截图失败），`renderer.info` / FPS 等运行时读数正常。因此**3D 的视觉回归不能靠这批截图断言**；本轮依据是「产物逐字节一致」。
3. **`presented` 相位口径**：本轮没有改变语义（D2 已回滚），但 harness 新增了 `presented-baked` 字段，只在实验分支出现，正式路径恒为 `null`。
4. **B4 未单独归因**，见 1.3。
5. **iframe 内 INP 恒为 0**：合成/跨文档事件不产生 Event Timing 条目，该字段不可用，报告里不当「很快」。
